# 分期执行细则（Playbooks）

## Playbook 1：死代码识别与清理（L1）

### 三层识别机制

| 层 | 手段 | 产出 |
|---|---|---|
| 静态扫描 | IDE/工具链引用分析；codegraph 调用图查零入边符号；grep 引用计数 | 零引用符号候选清单 |
| 运行时追踪 | 日志埋点、动态插桩、覆盖率工具、线上流量采样 | 路径可达性证据。**遗留项目常缺此基建——缺失时降级，置信度落到业务确认层** |
| 业务确认 | 静态无法定性项先按"预留 vs 废弃"启发式自判（见下），判不了的标 ⏳ 集中到门禁批量问人 | 决策依据记录（落盘 AGENTS.md） |

### 预留 vs 废弃 判定启发式（业务确认层的核心裁决）

静态扫描能给出"零引用/零实现"，但**定不了性**：是"作者有意留的扩展点"还是"重构遗留的废弃残留"？误判会删错代码。按以下信号判定：

| 信号 | 指向"预留（保留）" | 指向"废弃（可清理）" |
|---|---|---|
| 作者注释 | `@remarks 预留`/`TODO 未来`/`暂未实现` | `@deprecated`/无注释 |
| 成体系 | 接口 + 类型 + 枚举配套预留（如能力接口组、items.type 枚举） | 孤立单个符号 |
| 进 roadmap/README | 出现在路线图/计划里 | 对应已下线功能 |
| git 历史 | 近期新增、commit msg 含"扩展/预留/foundation" | 重构后留下、旧平台残留 |

**判定规则**：≥1 个"预留"信号 → 标 **预留**，落盘"作者声明预留，勿删"；无预留信号 + 有"废弃"信号 → 标 **废弃**，进清理建议（仍 L1 只出方案不删）；信号矛盾或全无 → **标 ⏳ 问人**，不擅自删。

> 真实案例（KnowNote）：`RerankCapability`/`ImageGenerationCapability` 接口零实现，看似废弃；但读源码注释 `@remarks 此接口为未来扩展预留,暂未实现` + 进 roadmap → 判定 **预留、保留**。同项目 `ollama-ai-provider` v1 依赖零引用、无预留信号 → 判定 **废弃、进清理**。靠此启发式避免了误删预留接口。

> ⚠️ 反面案例（评估实测，"静态零引用 ≠ 死代码"的铁证）：某 agent 在 L1 把 React i18n 基础设施（`I18nProvider` / `i18n` 初始化配置 / `LanguageSelector`）当"零引用死代码"删除——静态看这些文件没有直接 import 者。但全仓 `useTranslation()` 调用散落于 App / 对话框 / 卡片等十几个组件；删掉 Provider+配置后 i18n 未初始化，UI 文案全部退回原始 key（**静默损坏：应用照常启动，无报错无崩溃，但功能已坏**）。教训：对**配置 / Provider / 注册 / 注入**类符号，"零 import"是常态而非死信号——必须追"谁在消费它注入的能力"（运行时效果），绝不能只数 import 就删。这条正是 SKILL.md「L1 铁律：只诊断、不删除」的现实依据。

### 遗留项目高频死代码模式（排查清单）
- [ ] 复制粘贴旧平台/旧客户端改造留下的环境判断 if/else 残留
- [ ] 设计了但未落地的能力（如协同编辑、WebIDE 架构）的完整协议层
- [ ] 多轮重构不彻底留下的 N 套并存的消息通信/状态管理方式
- [ ] 功能迁移后（如前端 → Node 模块）新旧链路耦合、难以分辨生效路径
- [ ] 判断条件写在环境变量/配置中心的"开关代码"，静态看可达、运行时不可达
- [ ] 已下线业务的页面/接口/定时任务残留

### 纪律
- 每清理一块，同步在对应模块 AGENTS.md 记录"某功能已下线，相关兼容代码已移除"
- 不确定的一律进入人工确认清单，不凭静态引用下结论

## Playbook 2：架构瘦身（L1）

判断两问：**当前业务是否真实依赖这一复杂度？未来 6-12 个月是否有明确需求？**

| 阶段 | 动作 | AI 参与度 |
|---|---|---|
| 一期 | 下线未使用的协议层，保留最小可用通路 | AI 辅助分析，人工确认 |
| 二期 | 在简化后的通路上重构业务逻辑 | AI 主导方案，人工 review |
| 三期 | 基于新架构补自动化测试，锁定成果 | AI 全链路执行 |

注意：好的架构立足于现在，随业务变动调整；过度设计的复杂度会永久沉淀并误导 AI。

## Playbook 3：测试工程分期（L4）

| 期 | 目标 | 核心动作 | AI 角色 |
|---|---|---|---|
| 一期 | 测试骨架 | 引入测试框架、配置 Mock 环境、建立 fixtures | AI 主导方案 + 落地 |
| 二期 | MR 回归流水线 | 单测/E2E 流水线 + 构建镜像 | AI 辅导方案，需提供 CI 平台、构建体系等上下文 |
| 三期 | 核心链路覆盖 | 梳理 P0/P1/P2 用例，覆盖主流程 + 关键分支 | AI 整理用例，人工确认核心/非核心边界 |
| 四期 | 复杂场景补齐 | 多模块联动、异常链路、竞态条件 | AI 主导生成，人工 review |

### 实操要点
- 单测：基于 Mock 数据，覆盖简单功能
- E2E：多页面链路加载与交互；用线上真实环境时需配测试账号，且**测试后治理数据**（如清理测试产生的空项目，防止账号触上限）
- 上线初期人工辅助验证用例覆盖是否足够有效，稳定后放手
- 测试策略核心是"测什么"不是"写多少"——P0 主流程优先

## Playbook 4：视觉回归（前端项目，L4）

双层策略：
- **全页截图**：允许较高像素偏差 → 抓布局级异常（识别不了文字/圆角等小问题）
- **组件级截图**：严格像素偏差，覆盖组件各状态 → 抓精确样式问题

要点：
- baseline 截图跟随代码仓库存储，保证任何环境可复现比对
- 双层设计可防止 AI 为让流水线通过而误改样式——组件级严格偏差会在 MR 时暴露
- 前置条件：自动化测试框架已搭建（Playbook 3 一期完成后再上）

## Playbook 5：MR 智能门禁（L4）

三层校验：
1. **规范校验**：AI 评审规则文件（编码规范、设计约束），在 MR 流水线中对 diff 评审
2. **测试校验**：单测 / E2E / 视觉回归全部通过，失败即阻断合入
3. **影响面校验**：通过 codegraph 依赖图谱分析变更 blast radius（无 codegraph 时用 grep 引用计数兜底），高风险变更自动标记人工 review

AI 评审规则文件示例要点：
- 引用 `docs/conventions/` 下的规范文档作为评审依据
- 检查是否违反模块边界（场景外壳 → 共享层隐式穿透）
- 检查是否同步更新了受影响的 AGENTS.md（知识落盘规范的强制执行点）

## Playbook 6：债务治理常态化

- 通过 L2 规范确立持续治理方向，后续迭代中 AI 遵循新规范**顺手治理**历史问题
- MR 评审检测新增问题，防止新债务产生
- 把"周期集中的技术专项改造"变成"日常开发的常规化改造"
- 每月上下文漂移巡检（含指令臃肿审计）与债务台账一起 review

## Playbook 7：AI 操作边界盘点（L2）

上下文补“看不懂现状”，行为准则补“守不住纪律”，操作边界补“不能碰什么”——三面合围才防得住误改。边界是“只有人知道”的运行时真相，AI 的角色是**提问引导 + 格式化落盘**，不是猜测。

逐模块问三个问题：

1. **禁改**：有没有“看着能改、改了会炸”的路径？典型候选：已执行的数据库 migration、生成代码、vendored 三方源码、锁文件、CI 配置。
2. **高危**：哪些操作做了就难回头？典型：删依赖、改生产配置、schema 变更、force push、跳过测试合入。
3. **禁令**：有没有团队明令禁止的命令或流程红线？

落盘纪律：
- 全局边界进 `docs/conventions/module-boundaries.md`“AI 操作边界”节（模板见 templates.md）；模块特有红线就近进该模块 AGENTS.md“注意事项”，随目录注入而不占根文件预算
- 边界条目同样标注适用条件——业务下线、流程变更后，巡检臃肿审计要清理失效禁区，红线自己不能变成噪音
- 门禁时逐条与用户确认：**误列禁区会挡住正常开发，漏列禁区就是事故**
